## Codebase Patterns
- Todas las tablas financieras (transactions, wallets, balance_snapshots, categories) estan particionadas por `perfil` (TEXT). Cualquier query/metodo nuevo en db.py DEBE recibir `perfil` y filtrar por el, nunca leer/escribir sin ese filtro.
- `_ensure_wallets_for_profile(perfil)` se llama al inicio de casi cualquier metodo de billeteras -- crea las 4 billeteras (Bs/BDV, USD/Binance, USD/Efectivo, COP/Efectivo) en 0 si es la primera vez que se ve ese perfil. `is_new_profile(perfil)` debe llamarse ANTES de cualquier metodo que dispare esto, si se necesita saber si es la primera vez.
- Comandos nuevos en telegram_handler.py siguen el patron: `async def X_command(update, context)` -> `if not _is_allowed(update, context): return` -> obtener `db`/`perfil` -> logica -> `await _reply(update, texto)` (usar `_reply`, no `update.message.reply_text`, asi el comando tambien funciona como boton del /menu si se agrega ahi).
- Registrar todo comando nuevo en src/main.py: import + `application.add_handler(CommandHandler("nombre", funcion))`.
- Verificacion: `python3 -m py_compile src/bot/telegram_handler.py src/storage/db.py src/main.py` (compile check) + `.venv/bin/python -c "import src.main"` (smoke test de imports; el `python3` del sistema NO tiene `dotenv` instalado, hay que usar el venv). Para probar logica de db.py sin levantar el bot: `.venv/bin/python -c "from src.storage.db import DBClient; db = DBClient(db_path=':memory:', initial_balance=0, fixed_categories=['Otros']); ..."`.
- Personalidad de Coco: TODO texto fijo dirigido al usuario (comandos, errores) usa "usted" formal, tono de banquero de confianza, emojis minimos (solo los ya establecidos: 🐊 para la voz de Coco, y uno por seccion como maximo). Nunca "tu"/"tú"/"Intenta"/"Usa" informal -- usar "su"/"usted"/"Intente"/"Use". La voz LLM-generada (_persona_coco en prompt_builder.py) ya sigue este registro; los textos hardcodeados deben ser consistentes con ella (unificado en commit 5093de6).
- MONEDA_SIMBOLO y CUENTA_EMOJI (en telegram_handler.py) son los diccionarios de simbolos/emoji reusables para mensajes de saldo/transferencia.
- Nunca commitear .env ni *.db (ya estan en .gitignore). Nunca imprimir secretos reales en output visible.
- Para mandar un archivo (no solo texto) hay que usar `target.reply_document(...)` con `target = update.message or update.callback_query.message` (mismo patron que `_reply`, pero `_reply` solo soporta texto por ahora -- reply_document se llama aparte).

- Files changed: src/storage/db.py (nuevo metodo `delete_last_transaction(perfil)`), src/bot/telegram_handler.py (nuevo `deshacer_command`, agregado a /help y bienvenida), src/main.py (registrado el CommandHandler).

  - Alcance reducido a proposito: NO deshace ajustes de saldo directos (`set_wallet_balance`, usados por /saldo_inicial y frases tipo "tengo X en efectivo") ni `transfer()` (mueve dinero entre billeteras propias). Se dejo fuera para no arriesgar corromper saldos en una primera iteracion; si se pide extender /deshacer a estos casos, ese es el punto de partida.

## [2026-07-02] - US-003
- Implementados presupuestos por categoria: tabla `budgets` (perfil, categoria, limite_mensual, PK compuesta), comando /presupuesto (sin args lista, con "<categoria> <monto>" fija/reemplaza, con monto 0 elimina), y alerta automatica en la confirmacion de gasto (via `_budget_alert_line`) cuando el gasto acumulado del mes en esa categoria llega a 80% (aviso suave) o supera 100% (aviso directo) del limite -- tono banquero, una sola linea, sin emojis de alarma.
- Files changed: src/storage/db.py (tabla `budgets` en `_init_schema`, metodos `set_budget`, `get_all_budgets`, `get_budget_status`), src/bot/telegram_handler.py (`_budget_alert_line`, `presupuesto_command`, `format_confirmation_message` ahora acepta `budget_status` opcional, `_save_and_confirm` calcula el estado del presupuesto SOLO si `tipo == 'gasto' and moneda == 'Bs'` antes de armar el mensaje), src/main.py (registrado el CommandHandler).
- **Learnings for future iterations:**
  - Los limites de presupuesto son SIEMPRE en Bs (moneda del gasto del dia a dia en efectivo/BDV). Un gasto en USD o COP simplemente no dispara ni cuenta contra ningun presupuesto en esta iteracion -- si se quiere soportar multi-moneda en presupuestos habria que decidir una tasa de conversion consistente primero.
  - `get_budget_status(perfil, categoria, fecha)` retorna None si la categoria no tiene presupuesto fijado -- SIEMPRE chequear por None antes de leer 'porcentaje'/'gastado' (asi se evita calcular de mas en el camino feliz, que es el 99% de los gastos sin presupuesto configurado).
  - El calculo del mes usa `substr(fecha, 1, 7) = 'YYYY-MM'` sobre la columna `fecha` (no `created_at`), coherente con como /resumen ya agrupa por mes.
  - `ON CONFLICT(perfil, categoria) DO UPDATE` (upsert) es el patron a usar para tablas con PK compuesta (perfil, algo_mas) que se "fijan"/reemplazan en vez de acumularse -- mismo espiritu que wallets.
  - Testeado con DB en memoria: 420/500 -> 84% (aviso "va en 84%"), 620/500 -> 124% (aviso "ya superó"), categoria sin presupuesto -> None (sin aviso), set_budget con monto 0 elimina la fila, aislamiento por perfil verificado.

## [2026-07-02] - US-004
- Agregado aviso de variación relevante (>=3%) en la tasa BCV/Binance al consultar /cambio o /saldo. Se calcula al vuelo: cada vez que el cache de 1h vence y se refresca con un valor nuevo desde la API, se compara contra el valor que HABÍA en cache justo antes de sobrescribirlo. Si el cache sigue vigente (no hubo fetch nuevo), no hay variación que mostrar (no se inventa comparando contra algo mas viejo).
- Files changed: src/services/fx.py (`_get_rate_full` retorna `(rate, previous_or_None)`; `_get_rate` ahora es un wrapper que descarta el previo, sin romper a nadie que ya llamaba `get_bcv_rate`/`get_binance_rate`; nuevas `get_bcv_rate_with_variation`/`get_binance_rate_with_variation`), src/bot/telegram_handler.py (`_rate_variation_pct`, `_variation_note`, `_format_rates_block` ahora acepta `bcv_var`/`binance_var` opcionales; `cambio_command` y `saldo_command` usan las nuevas funciones *_with_variation; `resumen_command` se dejó SIN cambios, usa `get_bcv_rate`/`get_binance_rate` planas a propósito, ver abajo).
- **Learnings for future iterations:**
  - Alcance a propósito: solo /cambio y /saldo muestran variación (son las consultas "¿cómo está la tasa ahora?"). /resumen muestra las tasas solo como referencia de cierre de mes, no tiene sentido ahí y se dejó tal cual para no ensuciar ese mensaje.
  - Para testear esto sin llamar la API real: `db._conn.execute("UPDATE fx_rates SET fetched_at = '2000-01-01T00:00:00' WHERE page=?", (cache_key,))` fuerza que el cache se vea vencido, y luego se puede monkeypatchear `fx._fetch_rate_from_api = lambda page: <valor>` para controlar qué "nueva" tasa llega.
  - El umbral de 3% y el emoji 🔺/🔻 están en `_variation_note` (telegram_handler.py) -- si se quiere ajustar la sensibilidad del aviso, es el único lugar a tocar.
